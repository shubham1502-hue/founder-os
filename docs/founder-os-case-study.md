# Founder OS Case Study: From Messy GTM to Weekly Operating Cadence

This is a synthetic and fictionalized company example. It is not a production claim.

## Context

Fictional company:
A seed-stage B2B SaaS startup with founder-led sales, messy CRM, scattered customer feedback, slow onboarding, and investor update pressure.

The founder has enough activity to create noise, but not enough operating rhythm to convert that activity into decisions.

## Starting problem

- Accounts are researched manually
- Sales calls are not converted into learning
- Pipeline leakage is unclear
- Closed-won customers get stuck before activation
- Retention risks appear late
- Product feedback is scattered
- Weekly review is inconsistent
- Investor updates take too long

## Operating loop

Target accounts
-> GTM research
-> Founder-led sales call
-> Revenue leakage diagnosis
-> Customer onboarding
-> Retention and expansion
-> Product feedback
-> Weekly operating review
-> Board/investor update

## 7-day implementation sprint

- Day 1: Pick the operating problem and clean inputs
- Day 2: Run GTM or sales call module
- Day 3: Diagnose revenue or onboarding risk
- Day 4: Turn customer signals into product or retention decisions
- Day 5: Create weekly operating review
- Day 6: Convert key signals into investor narrative
- Day 7: Assign owners and update operating cadence

## Outputs created

- Account briefs
- Sales learning memo
- Revenue leakage diagnosis
- Onboarding attention queue
- Retention memo
- Roadmap decision queue
- Weekly operating review
- Board update

## Before and after

Before:

- founder memory
- scattered trackers
- no operating cadence
- unclear owners
- inconsistent investor narrative

After:

- decision artifacts
- weekly review rhythm
- owner-backed next actions
- founder-ready memos
- investor-safe narrative

## How a founder can use this

Start with the one operating problem creating the most drag this week. Fork only that repo if the problem is narrow. Use two to four modules only when the output of one naturally feeds the next.

For example, if outbound is messy, start with `ai-gtm-command-center`. If sales calls are happening but not creating learning, start with `founder-led-sales-call-os`. If customer feedback is scattered, start with `founder-product-feedback-roadmap-os`.

The lifecycle is a map, not a requirement.

## How a Founder's Office candidate can use this

Use this case study as a proof-of-work structure:

1. Pick a realistic company scenario.
2. Choose two or three Founder OS modules.
3. Replace sample inputs with synthetic or public-safe examples.
4. Run the workflows or adapt the templates.
5. Write a case note explaining the starting problem, outputs created, decisions made, and next owner actions.

The goal is to show operating judgment, not tool usage alone.
